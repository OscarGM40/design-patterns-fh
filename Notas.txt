Los patrones de diseño son soluciones comunes y probadas a problemas comunes

Si uso patrones de diseño tendré varias ventajas:
1- Son soluciones probadas, permiten evitar errores conocidos
2- Establecen un lenguaje común entre desarrolladores
3- Resuelven un problema con un código más limpio y efectivo

Patrón Strategy: múltiples métodos para resolver un mismo problema, y se elige dinámicamente según el contexto (recordar problema del cruce, lo dejamos tal cual si hay poco tráfico, pero si hubiera bastante hay que hacer una rotonda y si hubiera muchisimo tráfico hay que crear puentes para las diferentes direcciones, obviamente como cada una es más costosa hay que ver el contexto)

Patrones creacionales: ayudan a crear objetos de manera eficiente y flexible, ocultando los detalles de instanciación (esto es para todos?)
  Ejemplo: Singleton o Factory Method

Patrones de comportamiento: definen cómo los objetos interactúan y se comunican para cumplir tareas complejas
  Ejemplo: Observer o Strategy

Patrones estructurales: están enfocados en cómo componer clases u objetos para formar estructuras más grandes y reutilizables
Ejemplo: Adapter o Decorator.La idea  es que estos patrones ayuden a resolver un caso especifico. Recuerda que debe darse un problema concreto para implementar un patrón, siempre hay que ver si hay que aplicarlo

 Una closure es una función que encapsula una serie de variables y definiciones locales que únicamente serán accesibles si son devueltas con el operador return (de esta forma serían variables privadas). ESto se usaba sobre todo antes de la llegada de las clases con ECMA6, para crear entornos privados(ya no tienen mucho sentido)

 const miContador = (function() {
  let _contador = 0;
  const increment = () => ++_contador;  
  const decrement = () => --_contador;  
  const reset = () => (_contador = 0);
  const getContador => _contador;
  
  return {
    increment,
    decrement,
    reset,
    getContador
  }
 })(); // fijate que la clave es el return con lo que he creado. Es bastante obvio que esto se necesitó para hacer privado todo esto antes de las clases

 Esto es un closure(fijate que las IIFE son todo closures, esto no lo sabía, superinteresante). Fijate que esto no se lo lleva el garbage collector, y por ello consume más RAM.
 
 miContador.getContador(); // dará 0
 miContador.increment();
 Entiendo que la otra sintaxis diferente a las IIFE tmb es una closure pero con ésta queda mucho más claro que hacen (dejar un scope privado para lo interno, y que es como una clase o hook). Acuerdate que el garbageCollector no elimina nada durante runtime
